Fundamentals

Why store monsters as data, not code?

Imagine adding a new monster meant editing the attack code, the UI code, and the battle code. Every new monster would mean hunting through the whole project. MONSTER_DATA avoids that: add one dictionary entry, and every part of the game that reads from it — battle math, stat bars, evolutions — picks it up automatically.

📖 Data-driven design

Game content — monster stats, attack numbers, NPC dialog — lives in dictionaries, not scattered across methods. This is how Minecraft, Pokémon, and Stardew Valley actually store their content.

🧩 Classes as data + behavior

Monster holds data (health, stats, xp) and behavior (level up, take damage). The data comes from MONSTER_DATA; the behavior is the methods you write today.

Fundamentals

One multiplication makes every stat scale with level

MONSTER_DATA only stores a base stat — the value at level 1. Every method that needs the real, current stat multiplies that base by self.level.

Worked example: Sparchu's base attack is 3. At level 5, get_stat('attack') returns 3 * 5 = 15. At level 20 the same monster hits for 60 — no separate "level 20 stats" are ever stored, they're always computed from the base.

This is also why the stat guide keeps base numbers small (attack 1–6, defense 5–15) — those numbers get multiplied by level, sometimes by 30 or more, so a big base number becomes an enormous stat very fast.

Fundamentals — Step 2

What an attack dictionary actually controls

Every entry in ATTACK_DATA is read by the battle math in get_base_damage() and by reduce_energy() — four fields decide everything about how an attack behaves.

🎯 target

'opponent' to hurt them, 'player' to affect your own monster instead — that's how healing works, by targeting yourself.

💥 amount

Multiplies the attacker's attack stat. Above 1 deals damage; negative heals — -1.2 restores health instead of removing it.

⚡ cost

Energy spent from self.energy every time the move is used — reduce_energy() subtracts this directly.

🔥 element

Which animation and (later) type-matchup logic the move uses — 'fire', 'water', 'plant', or 'normal'.

Fundamentals — Step 8

update_xp: banking XP, and carrying the leftover

There are exactly two cases. Either the new XP fits below the level-up threshold, or it doesn't — and when it doesn't, the leftover XP (the part past the threshold) carries into the new level instead of being thrown away.

Worked example: a level 5 monster has level_up = 750 and xp = 0. Gaining 500 XP: 750 - 0 = 750, and 500 is not greater than that gap, so it just adds — xp becomes 500, level stays 5.

Now gaining 800 XP instead: the gap (750) is smaller than 800, so it levels up. Leftover XP is 800 - 750 = 50, becoming the new xp at level 6. level_up is then recalculated as 6 * 150 = 900 for the next level-up.

Fundamentals — Battles

One monster per side, a bench for the rest

A full Pokémon-style battle lets you switch monsters mid-fight and catch wild ones — that's a lot of extra menu logic. This battle system keeps it simple: only one monster per side is ever on screen. Your other monsters wait on the bench (monster_data), and the moment your active monster faints, the next one is sent in automatically.

It's still a real, properly turn-based fight — speed decides turn order, damage uses real type-effectiveness and defense math, and you can genuinely win or lose. Switching and catching are extension challenges if you want to add them yourself.

Fundamentals — Step 13

input(): reading the battle menu

Two nested menus. First selection_mode == 'general': Fight or Defend. Choosing Fight moves to selection_mode == 'attacks', listing whatever get_abilities(include_all=False) returns — only moves the monster can currently afford, straight from Step 6's work.

Confirming an attack doesn't deal damage directly — it calls current_monster.activate_attack(target, attack), which starts the attack animation. The actual damage happens later, in Step 15, once that animation finishes.

Since there's only ever one possible opponent on screen, there's no target-picking menu — get_target_group() (already written for you) figures out the target automatically from whether the move is self-targeting (heal) or not.

def input(self):
    if self.selection_mode and self.current_monster:
        keys = pygame.key.get_just_pressed()
        limiter = len(BATTLE_CHOICES) if self.selection_mode == 'general' else \
                  len(self.current_monster.monster.get_abilities(include_all=False)) or 1

        if keys[pygame.K_DOWN]: self.indexes[self.selection_mode] = (self.indexes[self.selection_mode] + 1) % limiter
        if keys[pygame.K_UP]:   self.indexes[self.selection_mode] = (self.indexes[self.selection_mode] - 1) % limiter

        if keys[pygame.K_SPACE]:
            if self.selection_mode == 'general':
                if self.indexes['general'] == 0:
                    self.selection_mode = 'attacks'
                else:
                    self.current_monster.monster.defending = True
                    self.update_all_monsters('resume')
                    self.current_monster = self.selection_mode = None
            elif self.selection_mode == 'attacks':
                abilities = self.current_monster.monster.get_abilities(include_all=False)
                if abilities:
                    attack = abilities[self.indexes['attacks']]
                    target_group = self.get_target_group(attack)
                    target = target_group.sprites()[0] if target_group.sprites() else self.current_monster
                    self.current_monster.activate_attack(target, attack)
                self.current_monster = self.selection_mode = None

        if keys[pygame.K_ESCAPE] and self.selection_mode == 'attacks':
            self.selection_mode = 'general'

        if keys[pygame.K_SPACE] or keys[pygame.K_ESCAPE]:
            self.indexes = {key: 0 for key in self.indexes}

Fundamentals — Step 15

apply_attack(): the real damage formula

This runs when the attack animation finishes (see MonsterSprite.animate() in sprites.py — already written, calling back into this method). Three ingredients combine into one final number:

🔥 Type effectiveness

Fire beats plant, water beats fire, plant beats water → amount *= 2. The reverse three matchups → amount *= 0.5. No rule matches → unchanged.

🛡️ Defense reduction

target_defense = 1 - defense_stat / 2000 — higher defense means a smaller multiplier, so less damage gets through. Choosing Defend subtracts another 0.2, clamped between 0 and 1.

Worked example: a monster with attack stat 30 uses spark (amount 1.1) against a plant-type target with defense stat 200. Base: 30 * 1.1 = 33. Type: fire vs plant → 33 * 2 = 66. Defense: 1 - 200/2000 = 0.9, so final damage is 66 * 0.9 = 59.4.
